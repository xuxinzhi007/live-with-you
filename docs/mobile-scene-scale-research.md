# 竖屏场景「房间很大」调研

> 日期：2026-10-20  
> 对照截图问题：上半空白墙、中间小窗贴片、底部家具缩成一条、角色浮在空地。  
> 目标：在 **390×844** 上做出「世界比手机大」的体感，而不是塞进联机大世界 / 房间列表大厅。

---

## 1. 现在为什么「感觉不大」

当前 Mobile 场景是**一屏装下整间房**：墙、窗、家具、双人都挤进同一 FOV。结果是：

| 区域（截图红框） | 现象 | 根因 |
| --- | --- | --- |
| 上半墙面 | 大片空白 | 没有纵深与遮挡，墙只是纯色矩形 |
| 中部窗户 | 像漂浮图标 | 家具用小贴图 + 百分比坐标，缺透视与尺度 |
| 底部家具带 | 像 UI 图标条 | 物件相对角色过小，脚底线与家具脱节 |
| 角色区 | 「站在空地」 | 地板只占底缘一条，中景没有可走带 |

**不是内容不够，是镜头策略错了：**  
竖屏手机 FOV 极窄，若坚持「一眼看完整间房」，世界就必然被压扁成示意图。口袋营地、月兔、桌面版雯宝都是用**镜头**制造大，而不是用更多地点按钮。

宪章与既有结论一致：打开时机是共处会话，不是每日联机大厅；大世界感来自**同房间可浏览**，不是陌生人房间列表。

---

## 2. 参考作怎么「变大」（可借 / 不借）

| 来源 | 可借 | 不借 |
| --- | --- | --- |
| 口袋营地 | 营地/小屋 **大于一屏**；拖移浏览；家具与角色同尺度 | 自由改俯仰角（营地其实也改不了） |
| 旅行青蛙 / 月兔 | 世界即界面；点物件进功能；墙面有材质与遮挡 | 把桌面一整屋无缩放塞进竖屏 |
| Honk / 陪伴类 | 在场感、相对站位清晰 | 做成纯聊天壳 |
| 分层视差文章（Makko 等） | 四带：远景 / 建筑中景 / **玩法带 1.0** / 前景遮挡 | 8 层乱视差（易晕） |
| 桌面版雯宝 | 已有手动平移 + 互动后温和跟镜头 | 原样搬到 Mobile 不改坐标体系 |

**一句话：**大 =「房间比屏幕宽（或深），我能拖着看」；不是「顶栏再加五个地点」。

---

## 3. 推荐设计方向（按投入排序）

### A. 镜头优先（强烈推荐，下一刀）

把小屋做成 **约 1.6～2.2 屏宽** 的可拖动画布：

```text
┌──────── 超出屏的墙 / 窗 / 柜 ────────┐
│     ░░░ 手机可视窗 ░░░              │
│         [我] [对方]                  │
└─────────────────────────────────────┘
     ← 横向拖移；双人共处时镜头跟「两人中点」
```

规则：

1. **玩法带固定在屏下 35–45%**：角色脚底对齐；家具同带同尺度。  
2. 默认镜头对准「我 + 对方」；玩家拖移后暂停跟随，点「一起做」或对方动作时温和拉回。  
3. 地点切换（小屋/阳台…）仍是换场景数据，不是换大厅。  
4. 共处站位槽改成**世界坐标**，再投影到屏上（协议仍可用槽 id）。

验收：不看 UI，只看画面，应觉得「还有半间房在旁边」。

### B. 尺度与分层（与 A 一起做）

四带（远→近）：

1. **远景**：墙色、窗外光、弱纹理（无点按）  
2. **建筑中景**：窗、门框、壁挂——尺寸要像建筑，不像图标  
3. **玩法带**：床、椅、角色、可点家具（同尺度）  
4. **前景**：极少（帘角、桌角遮挡），速率 ≤ 1.2×，勿挡脸

家具贴图至少抬到角色高度的 **0.6～1.2 倍**（关键件），禁止底条「emoji 货架」。

### C. 不做的

- 陌生人房间列表 / 匹配大厅当主路径  
- 为了「大」上 Three.js 全 3D 重建（成本高、和现有百分比家具冲突）  
- 在竖屏上追求「一眼看见整间房的桌面布局」

## 4. 你说的「TS 做特效」——多半是这些

口语里的「TS」常指 **TypeScript 生态里的 2D/骨骼运行时**，不是某种神秘语言：

| 技术 | 擅长 | 和雯宝关系 | 建议 |
| --- | --- | --- | --- |
| **PixiJS**（TS 友好） | 分层精灵、拖拽镜头、轻粒子、滤镜 | 最适合做「可拖房间 + 视差」 | **场景舞台优先候选** |
| **Spine**（有 spine-ts） | 角色骨骼 idle/walk/wave | 仓库已有 `docs/spine-integration.md` | **角色层**，设定稳后再接 |
| **GSAP / CSS** | 短 juice、面板、镜头缓动 | 现网共处 juice 已够用 | 继续用，不必换栈 |
| **Three.js** | 真 3D | 治愈 2.5D 房间过重 | 后置或不做 |
| **Live2D** | 立绘口型/表情 | 与现有立绘管线不同 | 非必须 |

结论：**空间感用 Pixi（或先用 DOM/CSS 平移画布）解决；角色呼吸感用 Spine；不要用 3D 引擎硬撑「房间大」。**

最小可行路径（不引入 Pixi 也能做）：

1. `.m-scene-world` 宽度 `180vw`，`overflow: hidden` 在场景区  
2. `touch` 横向拖 `translateX`  
3. 家具/角色改世界坐标；双人共处跟镜头  

Pixi 作为第二步：同一套坐标迁入 WebGL，再加视差与轻粒子。

---

## 5. 和多人共处的关系

- 「找对方」短码房 = 会话入口（已有），**不是**大厅。  
- 同房后舞台要大，是为了 **两人站位 + 家具可读**，不是为了 MMO。  
- 同步仍是：`sceneId + slot/worldPose + action`；先槽位，后自由坐标。

## 7. 移动 / 大世界：别用「走很久」撑大（案例）

竖屏上连续走路横穿大地图，普遍不友好。业界常用 **三层尺度**，而不是一种操作走遍一切：

| 尺度 | 玩家怎么动 | 竖屏案例 |
| --- | --- | --- |
| **房间内** | 短走（≤1～1.5s）到家具；或点家具瞬移到锚点再播动画 | 口袋营地：拖镜头看营地，点物件互动，不靠长跑 |
| **地点之间** | **瞬间进场**（门/地点条），可加 0.3s 淡入 | 旅行青蛙：庭院↔屋子是切场景；大世界是「旅行结果」不是你走路 |
| **更大世界** | **地图选点 / 路点传送**；首次可走路解锁，之后快传 | 《剑与远征：启程》：竖屏大世界 + 跑图探索，但远距靠传送点；Fast travel 设计也强调「先走到、再解锁传送」 |

参考链接（调研用）：

- 竖屏大世界论述：[网易 · 竖屏大世界](https://www.163.com/dy/article/J5AMSGIJ0526Q3CJ.html)（以《启程》为例：单手、绘本风、远距不靠纯走路）
- AFK Journey 预览：步行与 waypoint 传送并存（[Pocket Gamer](https://www.pocketgamer.com/afk-journey/preview/)）
- Fast travel 原则：先探索解锁，再传送，避免无聊重复走（[Waystones that respect the map](https://cobomakesgames.com/blog/fast-travel-design/)）
- 星露谷手游：点地行走，但是**横屏**农园，不证明竖屏适合长跑

**雯宝建议**

1. 现在：地点条 = 瞬切；共处/家具 = 短位移或锚点出现，不要「穿过整间屋」。  
2. 角色移动：只服务房间内气氛（走到窗边），超时就切到「已在位置」。  
3. 以后大世界：做 **地点图谱 / 路点**（小屋·街区·咖啡馆），不要做无缝可走大陆；和对方见面用已有短码房，进房后站位同步即可。

---

## 8. 决策一句

**竖屏要「房间很大」= 可拖的宽场景 + 玩法带同尺度家具 + 镜头跟共处，而不是大厅或 3D 大世界。特效栈优先 PixiJS（场景）+ Spine（角色）。大世界用「地图传送 + 房间内短走」，不要用长时间走路来证明世界大。**
