# 离线优先存档与云同步设计

## 目标

- 网络断开时，游戏仍可继续游玩并保存进度。
- 网络恢复后，客户端自动尝试上传本地进度；失败不影响游戏。
- 玩家可以在新设备上登录并恢复云端存档。
- 存档服务访问 MySQL，浏览器不直接连接数据库。
- 先支持单人、单世界快照；暂不建设实时联机或多人世界。

## 当前实现状态

- 游戏状态主要保存在浏览器 `localStorage`。
- `src/game/world-save.js` 会收集部分游戏状态，形成版本化快照并写入 `wenbebi-world-v1`。
- 配置 `VITE_WENBEBI_SAVE_URL` 后，客户端会尝试 `POST` 快照；上传失败不会中断游玩。
- 上传失败没有持久化的重试队列；客户端没有接入云端读取、账号、冲突处理或同步状态提示。
- 项目有 PWA Manifest，但目前没有 Service Worker 离线资源缓存。已缓存过网页和“首次断网打开网页”是两种不同能力。

以上是当前代码状态，不代表云存档闭环已经上线。

## 推荐架构

```text
手机或电脑浏览器
  ├─ 本地游戏状态与待同步存档
  └─ HTTPS → Netlify Function / 存档 API
                 → 受保护的 HTTPS 隧道
                 → N100 上的存档服务
                 → N100 内网 MySQL
```

浏览器只访问 HTTPS 存档接口。MySQL 只允许后端服务通过内网访问，不向公网开放 3306。Netlify Function 与存档服务之间的服务密钥保存在服务端环境变量中，不进入前端构建产物。

### N100 的定位

- **个人测试阶段**：N100 可以运行 MySQL 和独立的存档 API。外部访问只到 API，不能穿透到数据库端口。
- **长期公开运营**：建议把正式存档 API 和数据库部署到稳定的云端；N100 可继续运行 Ollama，或作为备份目标。若继续以 N100 为唯一存档主机，家中断电、断网或设备维护期间，云端读写会暂停；客户端仍保留本地进度并等待重试。

## 客户端存档流程

1. 游戏操作先写入本地，绝不等待网络。
2. 本地状态变化后，生成最新世界快照并标记为待同步。照片二进制不放进世界快照。
3. 联网、游戏启动、页面回到前台时尝试上传；可提供手动重试入口。
4. 上传成功并收到服务端版本确认后，更新本地已同步版本。
5. 上传失败时保留待同步状态，采用逐步延长间隔的重试策略；多次离线期间的旧快照可合并为最新快照。
6. Service Worker 后台同步可作为增强，但不能作为唯一重试机制；浏览器可能暂停或终止后台任务。

### 本地存储迁移

当前游戏状态分散在多个 `localStorage` 项中。迁移时先保留旧数据读取能力，将现有数据转换成带 `schemaVersion` 的世界快照；迁移完成并验证可恢复前，不删除旧存档。

待同步队列应持久化，建议使用 IndexedDB。初期可以继续由现有运行时写入本地状态；应用启动时重新收集快照，并与最后确认的服务端版本或内容摘要比较，发现差异就补入队列。这样可覆盖本地保存成功、但页面来不及更新待同步队列就被关闭的情况。后续再逐步把存档读写统一到一个存储模块。

## 服务端与版本冲突

云端档案必须关联经过验证的玩家身份。`deviceId` 只用于区分设备，不是登录凭证；客户端提交的 `accountId` 也不能作为授权依据。

建议快照至少包含：

```json
{
  "schemaVersion": 1,
  "updatedAt": 1730000000000,
  "deviceId": "client-device-uuid",
  "state": {}
}
```

上传请求还应携带幂等请求编号和客户端已知的 `baseRevision`。服务端根据已验证的登录会话确定玩家，校验快照大小、结构与版本后写入 MySQL，并返回新的 `revision`。如果服务端版本已变化，则返回冲突，不得静默覆盖较新的云档。

客户端发现冲突时保留本地和云端两份数据，提供明确的恢复选择；不通过设备时间简单判断新旧，也不自动合并互相矛盾的整份快照。读取云档只在本地没有存档或玩家主动选择恢复时进行，避免覆盖离线进度。

MySQL 初期可按“每个玩家一份当前快照”存储，保留 `player_id`、`revision`、`schema_version`、快照内容和服务端更新时间。之后若需要历史回档，再增加版本历史表或备份策略，不把事件溯源作为第一阶段前置。

## 安全、隐私与备份

- 之前在聊天中出现过的数据库管理员凭据应视为已暴露：更换凭据，并为游戏建立独立数据库和最小权限应用账号。
- 数据库账号与服务密钥仅放在后端环境变量或受保护的服务配置中；不要使用 `VITE_` 前缀保存秘密。
- 对接口实施身份校验、请求体大小限制、结构校验、写入频率限制和 HTTPS 传输。
- 照片继续只保存在本机；未来若需要跨设备照片，再单独设计媒体上传、授权和删除流程。
- 建立自动备份，并定期验证备份确实可以恢复。数据库可用不等于备份可恢复。
- 正式面向用户前，补齐账号注销、存档导出/删除和必要的隐私说明。

## 分阶段实施

### 阶段一：个人离线优先版本

- 继续兼容当前 `localStorage` 存档。
- 增加持久化待同步队列、启动/联网/回到前台重试和同步状态提示。
- 在 N100 部署独立存档 API，通过 HTTPS 隧道访问 MySQL；数据库端口保持内网封闭。
- 完成快照上传、云端读取和手动恢复。

### 阶段二：可跨设备使用

- 接入玩家登录与会话校验，一个玩家对应一个云端档案。
- 增加服务端 revision、冲突检测和用户可控恢复。
- 完成 IndexedDB 存档迁移、导入导出和本地数据恢复测试。
- 加入 Service Worker 静态资源缓存，验证安装后断网重开。

### 阶段三：长期运营

- 将正式 API 和 MySQL 迁到稳定云端，或明确 N100 主机故障期间的服务降级方案。
- 建立监控、日志、频率限制、自动备份和定期恢复演练。
- 管理数据库迁移、账号注销、数据导出与删除。

## 验收标准

- 飞行模式下可以继续游玩，刷新后本地进度仍在。
- 网络恢复后，待同步状态会自动消退；失败时仍保留本地进度并显示可重试状态。
- 已安装且缓存过资源的游戏可断网重新打开；首次访问时离线打开不作保证。
- 新设备登录后可以显式恢复云端档案。
- 两台设备修改同一档案时，服务端能检测版本冲突，不会静默丢档。
- 公网扫描不到 MySQL 3306，前端构建文件中没有数据库密码或服务端密钥。
- 备份恢复演练能够还原一份有效游戏存档。
