# data-service 代码审核规范

> 本文件是审核清单，编号 **REV-01–REV-09**。仓内成文规范用另一套 **R01–R18**（落点见 `../../../references/project-index.md`）。两边同时在场时听仓内规范，本清单不顶替它，只补仓内没写的项。仓内规范与 `$PERSONAL_AGENTS_MD` 都为空时，才逐条用下面的 REV 条目，不臆造第三套编号。

## 审核流程

**先定范围，再按下列顺序输出**：默认审 `git status`/`git diff` 的未提交改动；用户指定 commit 范围（如 `HEAD~1..HEAD`）时按指定范围。变更概览表只列范围内文件，REV-07 影响面评估同样锚定该范围，不外溢到全仓评估。

执行审核时按以下顺序输出：

```
### 1. 变更概览
| 文件 | 类型 | 影响域 |
|------|------|--------|

### 2. 分层合规检查
### 3. SQL 与查询约束检查
### 4. 生成文件保护检查
### 5. 事务与并发安全检查
### 6. 接口与错误处理检查
### 7. 影响面评估
### 8. 测试覆盖检查
### 9. 总结与建议
```

## REV-01 — 分层架构硬约束

逐文件检查变更是否符合分层：

| 层 | 允许 | 禁止 |
|---|------|------|
| `internal/service` | 参数校验、协议适配、错误转换（Kratos errors） | 业务逻辑、DB 操作、外部调用 |
| `internal/biz` | 业务编排、usecase、repo interface 定义 | 直接操作 DB/Redis/MQTT |
| `internal/data` | DB/Redis/MQTT/外部依赖实现 | 业务规则判断 |
| `internal/server` | HTTP/gRPC/MQTT/Scheduler 组装 | 任何业务逻辑 |

**检查点：**
- `service` 层是否出现了业务判断（状态机、规则计算）？
- `biz` 层是否直接操作了 `gorm.DB` 或外部客户端？
- `data` 层 SQL 是否包含了业务逻辑（可在 Go 层完成的状态判断、规则计算）？

---

## REV-02 — SQL 与查询约束

检查 `internal/data` 层的所有 SQL：

- [ ] SQL 只承担持久化、基础筛选、排序、分页和聚合
- [ ] 业务逻辑（状态判断、规则计算、结果组合）在 `biz` 层用 Go 实现
- [ ] 无非必要子查询（仅在简单/批量查询无法保证正确性时允许）
- [ ] 表关联最小化，范围控制在满足查询条件的最小集合
- [ ] 附属/展示属性通过批量查询回填，非 JOIN 获取
- [ ] 回填时使用批量查询，无 N+1 问题
- [ ] 关联查询仅用于：关系参与业务筛选、权限/可见性判断、存在性判断、聚合、保证分页排序正确

## REV-03 — 生成文件保护

以下文件禁止手动修改：

```
api/**/v1/*.pb.go
api/**/v1/*_grpc.pb.go
api/**/v1/*_http.pb.go
api/**/v1/*_errors.pb.go
openapi.yaml
cmd/data-service/wire_gen.go
```

**检查点：**
- 变更列表中是否包含上述文件？如包含，是否通过命令生成？
- 修改 `.proto` 后是否重新生成？命令以 `$REPO/Makefile` 的目标为唯一正确副本（单文件生成需要 `PROTO=` 参数，裸跑会静默空转）；工程约束文件落点按 `../../../references/project-index.md` 解析，不假设某个 IDE 的目录名。
- 修改配置 proto 后是否执行了 `make config`？
- 新增/调整依赖注入后是否执行了 `cd cmd/data-service && wire`？

## REV-04 — 事务与并发安全

**事务边界：**
- 多步 DB 操作是否有事务保护？
- 事务内是否包含外部调用（RPC/MQTT）？（不应包含）
- 事务失败后的数据一致性是否可接受？

**并发安全：**
- goroutine 是否有明确的生命周期控制（context timeout、errgroup）？
- 共享状态是否有 mutex 保护？
- goroutine 内的 panic 是否被 recover？
- fire-and-forget goroutine 是否有超时保护？

**分布式锁：**
- 并发写同一资源是否使用了分布式锁？

## REV-05 — 接口与错误处理

- [ ] 接口变更先在 `api/<module>/v1/*.proto` 定义，不直接改生成产物
- [ ] 函数参数或返回值超过 3 个时，是否改为结构体？
- [ ] 错误包装使用 `%w`（service 层转为 Kratos 错误）
- [ ] `context.Context` 作为第一个参数，跨边界显式传递
- [ ] 新增工具函数前先检查 `internal/pkg/helper` 是否已有
- [ ] 初始化阶段确定性错误可用 Must；外部依赖失败必须显式处理

---

## REV-06 — 禁止项

- [ ] 无只调用一次的几行小函数（内联到调用方）
- [ ] 无全局状态引入（保持显式注入）
- [ ] 无散落在 service/biz/data 层的工具函数（应在 `internal/pkg/helper`）
- [ ] 无手写解决生成文件冲突（应重新生成）

## REV-07 — 影响面评估

每次审核必须输出影响面：

```
### 影响面

**直接影响：**
- 涉及的 API 端点
- 涉及的数据库表
- 涉及的消息队列 topic

**间接影响：**
- 上下游服务依赖
- 前端展示变化
- 已有功能的隐式行为变更

**行为变更（Breaking Change）：**
- 之前允许的操作是否被拒绝？
- 之前拒绝的操作是否被允许？
- 返回值结构是否变化？

**风险等级：** 高/中/低
**回滚方案：** ...
```

## REV-08 — 测试覆盖检查

- [ ] 新增功能是否有对应的单元测试？
- [ ] 行为变更（Breaking Change）是否有测试覆盖旧行为和新行为？
- [ ] Mock 是否完整覆盖了依赖接口的所有方法？
- [ ] 测试是否使用 `t.Parallel()` 并发执行（无共享状态时）？

## REV-09 — 代码风格

- 面向过程脚本风格，极少注释（代码即文档）
- 函数命名清晰，自解释
- 变量命名简洁，避免无意义缩写

---

## 开发指导模式

当用于开发指导（非审核）时，额外执行：

1. **先查后写**：检查 `internal/pkg/helper`、现有 repo 接口、已有 Usecase 方法，优先复用
2. **分层落位**：新功能按 api → service → biz → data 顺序创建
3. **Wire 注入**：新增依赖后执行 `cd cmd/data-service && wire`
4. **生成对齐**：修改 proto 后执行对应生成命令
5. **go 文件后**：执行 `gofmt` + `goimports`
