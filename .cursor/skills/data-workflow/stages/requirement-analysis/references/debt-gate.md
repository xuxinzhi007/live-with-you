# 负债与风险判定细则

`../../requirement-analysis/SKILL.md` 的九项前置评估在这里给判定标准。**本文件只有判定方法，没有业务取值**；涉及具体文件、符号、索引时回代码核对。

## 怎么用

1. 选方案之前读一次，逐项记结论（通过 / 阻塞 / 风险已知）。
2. 每项结论必须带依据：`文件:符号`、命令输出、或用户明确拍板。
3. 判「阻塞」的项目，在需求阶段停下报告；不许带进技术方案再处理。

---

## 1 可维护性

**数什么**

| 指标 | 怎么数 | 通过线 |
|---|---|---|
| 跨层依赖 | service 里出现 DB/外部调用；biz 里出现 `gorm.DB`；data 里出现业务判断 | 0 |
| 复制逻辑 | 同一段判断/转换在仓库里出现第几次（grep 关键表达式，不凭印象） | 第 2 次必须引用已有实现；第 3 次才允许抽象 |
| 新增导出符号 | 新增函数/方法/结构体的数量 | 能说清每个符号的唯一调用方 |
| 分支增量 | 新增 if/switch 分支数 | 与需求一一对应，没有「顺便」分支 |

**收口方案要指到具体函数**，不是「抽个 helper」。新建 helper 包本身也是债：先 grep `internal/pkg/helper` 是否已有同语义函数。

**不通过的样子**：新增一个只做参数转换的 DTO、为一次筛选铺的 normalize helper、跨模块签名改动只为塞一个边界判断。

---

## 2 技术债

**还债**：删重复、合并平行实现、补测试、拆过长函数。
**欠债**：临时开关、兼容分支、TODO、手工运维步骤、双写、回填脚本。

欠债必须写三件事，缺一即阻塞：

```
落点     <文件:符号> 或 <issue/技术债清单条目>
怎么还   <动作：删哪段、合并哪两处、补哪条测试>
何时还   <触发条件：如「下个版本」「流量超 X 时」「该开关下线时」>
```

**不通过的样子**：「先这样，后面再优化」；写了 TODO 但没有归属人和触发条件。

---

## 3 长期演进成本

**六个月测试**：假设半年后要加一个筛选维度 / 一个数据源 / 一个状态，需要改几个文件？

- 逐个数出来（`文件:行` 级别），不要估。
- ≤3 个文件 → 通过。
- >3 个文件 → 必须给收口点（配置化、表驱动、统一入口），并写进「已知代价」说明为什么这次不做。

**不通过的样子**：「以后再说」；每加一个数据源复制一份 Usecase 而没有任何抽象计划。

---

## 4 回滚可行性

分三类分别回答，不要合并：

| 类别 | 要回答 | 阻塞条件 |
|---|---|---|
| 代码 | 一个 revert 能否独立生效？是否依赖同一 MR 里的其他提交？ | 回滚会连带丢功能且无替代 |
| 数据 | 新增字段/表是否可空？有回填吗？回填可逆吗？状态迁移能退吗？ | 不可逆且无备份/无快照 |
| 外部 | MQTT/通知/第三方回调会不会在回滚后继续产生副作用？ | 幂等或重放能力缺失 |

输出带编号的回滚步骤，每步给命令或操作位置。**「回滚 = git revert」只覆盖第一类，不能当完整答案。**

---

## 5 灰度 / 降级

**四问**：开关在哪？关掉后行为是什么？默认值是开还是关？关掉会影响谁？

允许「不需要开关」的情形只有三种，必须点名属于哪一种：

1. 只读路径（不改变状态）；
2. 纯幂等写（重复执行结果一致）；
3. 可重放（失败可按原输入重跑）。

其余情况判阻塞。**反向也成立**：不得为了假想未来提前加开关/灰度（项目规则禁止投机式配置）。

---

## 6 容量与性能预算

**必算三个数**：当前量级、本次增量、×10 后的瓶颈点。

查询三问（逐条回答，答不出即阻塞）：

1. 走哪个索引？索引名或字段顺序写出来。
2. 扫描行数量级是多少？（`EXPLAIN` 或表规模估算）
3. 分页是否深翻页？`OFFSET` 上限是多少？

**口径一致性**：COUNT 与 LIST 是否共用 `baseQuery`；导出/统计是否与列表口径一致；聚合是否排除了中止态/剔除态（业务口径问知识层，取值回代码）。

---

## 7 安全威胁（需求阶段只答三问）

1. **越权**：这个需求新增了哪个"按 ID 取数据"的入口？资源归属校验复用哪个 `apply*Scope`？点名到函数。
2. **外部输入**：哪些字段会进 `Where` / `Raw` / `Order` / `Table` / 文件路径？
3. **日志与响应**：新增日志会不会带 token、手机号、凭证、完整客户数据？错误信息会不会把内部细节透给调用方？

三问都答了才算通过。答不出「复用哪个 scope」，就是新增了一条越权路径。

---

## 8 DoD（验收标准）

合格写法四要素：

```
命令      <可粘贴执行的命令>
期望      <期望输出的关键行/字段/退出码>
执行人    谁跑（自己 / 测试 / 前端联调）
观测点    在哪看结果（终端 / 页面 / 日志 / 指标）
```

**不合格**：「功能正常」「测试通过」「联调 OK」「符合预期」。这类 DoD 会让后面所有门禁变成猜谜——`quality-gate` 只能照着它验，它模糊则门禁模糊。

---

## 9 测试策略

按改动类型查表，每类都要点名到包/文件/端点：

| 改动类型 | 必跑 | 点名要求 |
|---|---|---|
| proto / service | `tests/api` 相关端点 + 生成物一致性 | 端点的 HTTP path 或 RPC 名 |
| biz 规则分支 | 单测 | `internal/biz` 下的包与用例名 |
| data / SQL | 单测 + 索引预检 | 方法与索引名 |
| 状态机 | 写入口一条 + 读侧一条 | 状态族（带表名/字段名限定） |
| 纯配置（非 embed） | diff 条目校验 | 改动条目在整体结构中的位置 |
| 纯文档/注释 | 不跑 | 写明「无代码改动」 |

**只写「加单测」判不通过**：既没说哪个包，也没说断言什么。

---

## 输出格式（决定表）

九项结论合成一张表，跟着一页方案走：

```
| # | 项 | 结论 | 依据 | 缓解措施 | 阻塞 |
|---|----|------|------|----------|------|
| 1 | 可维护性 | ✅ | 复用 helper.ResolveXxx；新增跨层=0 | — | 否 |
| 2 | 技术债 | ⚠️ | 欠债：internal/biz/xxx.go 兼容分支 | 下个版本删除，触发条件=开关下线 | 否 |
| 4 | 回滚 | ❌ | 表 tb_xxx 新增列不可逆，无备份 | — | 是 |
```

「依据」列不接受「已检查」「符合规范」这类词；必须是文件符号、命令输出、或用户拍板原话。

---

## 常见错法（见到就打回）

- 九项写成一段散文，没有逐项判定。
- 判定用「低/中/高」但没给触发条件与后果。
- 只给一个方案，且它就是「加一层」。
- 回滚只写 `git revert`。
- DoD 是「功能可用」。
- 测试策略是「补充单元测试」。
- 把实现细节（用 map 还是 slice）列成待拍板问题，而把真正的决策（要不要新增表）自己定了。
