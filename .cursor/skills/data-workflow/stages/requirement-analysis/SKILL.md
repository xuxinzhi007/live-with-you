# Requirement Analysis（需求 + 负债双评估）

编码前分析需求。落 `spec.md` 前读 `../../references/doc-shape.md`：这篇的主活是拍板，第一屏只有本质一句话和已拍板的决定。目标不是写长方案，而是回答两个问题：

1. **现状是什么** —— 只能来自代码与知识层，不许来自记忆。
2. **这次改动是资产还是负债** —— 必须有判定标准，不许「符合规范」式结论。

第二个问题必须在**选方案之前**答完。方案定型后再问「设计合理吗」，只能挑毛病，改不了方向——那是 `../change-review/SKILL.md` 的事，不是需求阶段的事。

## 值不值得做

写方案之前先按 `../../references/scope.md` 定级。写不出来，或答案是「以后可能会用到」，停，用 `wait` 把最小做法交给对方。不进九项，不进技术方案。L1 不要为了填本文件而升到这里。

- 不做这次改动，谁受影响、以什么频率、错一次的代价是什么。
- 一次配置、一次数据修复或一句说明能否解决。能，就不做这次改动。

一年只发生两次、错一次只是多一次人工确认的事，不进 feature 主链。每周都发生、错一次会进入不可恢复终态的事，才进。这条不放开 `api/`、proto、状态、租户权限、回滚上的写入门：那些路径仍然不能用 `change` 绕过 hook。

## 先看口径

分析前按需查这些来源，不要只凭需求文字猜：

- `api/**/*.proto`：接口和字段事实来源。
- `docs/API`：HTTP 入参、出参、前端使用口径。
- `docs/architecture`：跨模块流程和架构约束。
- `internal/service`：参数校验、协议适配、错误转换。
- `internal/biz`：业务规则、编排、Repo 接口。
- `internal/data`：DB 查询、外部依赖适配。
- `configs/tag/system_tags.json`：系统标签、枚举类业务配置。

业务口径走知识层 `$KNOW`（会话开头由 L0 执行 `eval "$(bash scripts/paths.sh)"` 解析；单独进入本技能时先自己解析一次，解析为空就只读代码 + 仓库 `docs/`，并声明「知识层未配置」后继续，不许猜绝对路径）。

如果需求涉及 Go 实现，后续编码前再读 `../implementation/references/go-style.md`；完成 Go 改动前读 `../implementation/references/reuse-gate.md`。拍板用全局技能 `grilling`。一页方案确认后再读 `../tech-design/SKILL.md` 填公司模板。

## 两个产出，一次交付

| 产出 | 内容 | 来源约束 |
|---|---|---|
| **事实清单** | 现状：已有能力、入口、数据、调用方、约束 | 每条带 `文件:符号`；无出处的进「待确认」 |
| **决定表** | 要做什么 / 不做什么 / 怎么验证 / 怎么回滚 / 欠了什么债 | 每条必须用户拍板；agent 不自填 |

事实与决定**不许混写**：事实段出现「建议/应该」，说明在替用户做决定；决定段出现没读过的代码路径，说明在拿假设当事实。

## 九项前置评估（选方案之前必须答完）

逐项给结论，不写「符合规范」。任一项判**阻塞**且无缓解措施，停在需求阶段，不进技术方案。判定细则见 [`references/debt-gate.md`](references/debt-gate.md)，动手前读一次。

### A 维护性：这次改动是还债还是欠债

| # | 问句 | 判定 |
|---|---|---|
| 1 | **可维护性**：新增跨层依赖、复制逻辑、跨层 import 各几处？复杂度是否上升？ | 跨层依赖=0、复制逻辑=0；否则必须给收口方案（复用哪个已有函数） |
| 2 | **技术债**：这次是还债还是欠债？欠的记在哪？ | 欠债必须写清「在哪、怎么还、何时还」三件事，缺一即阻塞 |
| 3 | **长期演进成本**：6 个月后再加一个维度，要改几个文件、几处判空？ | ≤3 文件；>3 必须给收口点，或明确写进「已知代价」并说明接受理由 |

### B 可运营性：出事能不能兜住

| # | 问句 | 判定 |
|---|---|---|
| 4 | **回滚可行性**：代码回滚几步？数据回滚几步？能不能只回滚一半？ | 数据不可逆且无备份 = 阻塞；输出带编号的回滚步骤 |
| 5 | **灰度/降级**：出问题能不能关掉？开关在哪？默认值是什么？ | 「不能关」必须属于三种允许情形（只读 / 纯幂等写 / 可重放），否则阻塞 |
| 6 | **容量与性能预算**：QPS/数据量 ×10 时瓶颈在哪？新增查询走哪个索引？ | 新增查询无索引依据、COUNT 与 LIST 口径不一致 = 阻塞 |

### C 可信性：怎么算做完、怎么证明

| # | 问句 | 判定 |
|---|---|---|
| 7 | **安全威胁**：新增了哪些越权入口、外部输入、日志字段？ | 三问都要答；资源归属必须点名复用哪个 `apply*Scope` |
| 8 | **验收标准 DoD**：什么算做完？用哪条命令、看哪个输出证明？ | 无可执行证明的 DoD 不算 DoD |
| 9 | **测试策略**：单测覆盖哪个分支、接口测试覆盖哪个端点、回归到哪？ | 只写「加单测」= 未通过；必须点名包/文件/端点 |

九项里有 **3 项以上无法判定**，说明需求信息不足：停下来要信息，不要硬写方案。

## 方案对比（防止第一直觉锁死）

候选方案**至少两个**，其中一个必须是**最小改动**（不加表、不加字段、不加开关、不加中间层）。每个被排除的方案写排除理由，理由必须指到第 1–9 项中的具体哪一项不合格。

只给一个方案 = 没有做分析。项目里那些「顺手加个中间层 / 一次性 normalize helper」都是这么来的。

## 分析步骤

1. 判定需求归属：新能力 / 已有能力扩展 / 筛选条件 / 状态流转 / 数据修正 / 权限控制 / 展示字段补齐。
2. 找现有能力（复用门禁前置）：proto、docs、service/biz/data 里是否已有字段、RPC、状态、标签、Repo 方法、查询条件。能复用就写「复用现有 `<文件:符号>`」。
3. 收窄本质：一句话写清，避免被需求名词带偏。
4. 逐项判断是否需要新增：字段、RPC、表字段、配置、索引、状态、错误码、文档。新增前必须解释为什么现有能力解决不了。
5. 拆接口变更：只写核心字段与兼容性影响，先落 `api/<module>/v1/*.proto`，不从 service/data 倒推。
6. 拆后端流程：`service → biz → data` 写 3–6 步。service 只做校验与协议适配，biz 写规则与编排，data 只做持久化、筛选、排序、分页、聚合。
7. **九项前置评估**（上一节），逐项落结论与依据。A 组三项可先粗判，第 1/3/4/6 项等第 8 步的证据回来再定稿。
8. **影响面评估**：调用 `../impact-assessment/SKILL.md`，产出 `specs/<feature>/impact.md`。四轴（调用方 / 状态机 / 租户权限 / 回滚）+ 维护性三查，**每项要么带 grep 证据，要么标 UNVERIFIED**——标了 UNVERIFIED 的项不许在决定表里当已知条件用。
9. **方案对比**（上一节），两个以上，含最小改动。排除理由指到第 1–9 项，影响面清单里「受影响能力 N 个、其中共享型 M 个」是最常用的排除依据。
10. 标出待拍板点 → 用 `grilling` 拷问（一次一问、按依赖顺序、每问附推荐答案、能从代码查到的不问用户）→ 清零后写一页方案 → 拍板后按全局技能 `to-spec` 写 spec。

## 什么时候派子 agent 调研

需求分析里最容易翻车的一步是「现状是什么」：主 agent 边搜边猜，搜到一半就把假设当事实写进方案。判据：

| 情形 | 做法 |
|---|---|
| 2 个以上**互相独立**的现状问题（例：调用方有哪些 / 历史数据长什么样 / 有没有现成开关），彼此不依赖对方结论 | **并行派只读子 agent**，一个 agent 一个问题，各自回 `文件:符号` 级证据 |
| 只有一个问题，或问题之间有依赖（后一个要拿前一个的结论当输入） | 主 agent 自己 Grep/Read，不派发 |
| 需求要拍板、要选方案、要下结论 | **不派**。判断留在主 agent，子 agent 只交事实 |

派发纪律（细则见 `../../references/subagent-protocol.md`）：brief 里写清目标、边界、必答、禁止，**不塞业务事实**（塞进去会锚定它的结论，覆盖率反而下降）；子 agent 只读，不许改文件；回收时逐条核对证据能否指到 `文件:符号`，指不到的降级为「待确认」，不进事实清单。

## 门禁（阻塞项，不自行绕过）

命中任一条，停在需求阶段并明确报告，不进技术方案：

- 第 2 项：借债但没有落点
- 第 4 项：数据不可回滚且无备份
- 第 6 项：新增查询无索引依据
- 第 7 项：存在未覆盖的越权路径
- 第 8 项：DoD 无可执行证明
- 第 9 项：测试策略只有「加单测」
- 方案对比：只有一个方案，或没有「最小改动」
- 影响面：`impact.md` 缺失，或四轴里有一轴整轴标 UNVERIFIED 就下了结论

## 输出（一屏）

```
需求分析
本质        一句话
归属        ...
现状        已有能力：<文件:符号> ×N；缺口：...
影响面      受影响能力 N（共享型 M）｜状态机 有/无新增值｜权限 口径｜回滚 可逆/不可逆
方案        A 最小改动（...）/ B ...（排除理由：第 x 项不合格）
九项        1 ✅  2 ⚠️欠债→落点  3 ✅ | 4 ✅  5 ✅  6 ⚠️ | 7 ✅  8 ✅  9 ✅
不做        明确边界
待拍板      ×N（每条附推荐答案）
门禁        通过 / 阻塞于第 6 项
工件        specs/<feature>/{impact,spec}.md
```

需求很小时压缩为：核心结论、本质、改动范围、九项结论（一行）、待确认。

## 判断规则

- 能加筛选就不要新增流程。
- 能复用状态就不要新增枚举。
- 能复用主表字段就不要新增关联表。
- 能在 biz 组合就不要把业务规则塞进 SQL。
- 能批量查询就不要 N+1。
- 不为了未来扩展加灰度、开关、中间层或配置。
- **借债必须留痕**，不许「先这样，后面再说」。
- **方案对比里没有「最小改动」，视为未做分析。**
- **影响面没有证据，视为没有影响面**——UNVERIFIED 不是「大概没影响」。
- 不把另一个历史方案默认纳入当前需求；范围不清时先问。

## 自查（输出前）

- 每条事实能否指到 `文件:符号`？
- 九项是否逐项给了判定与依据，而不是一句「符合规范」？
- 是否有两个以上方案，排除理由指到具体项？
- `impact.md` 的四轴是否都有证据或诚实的 UNVERIFIED？
- DoD 别人能不能照着执行、得出同样结论？
- 待拍板是否只剩真正影响行为、成本或兼容性的决策？
- 是否把「实现细节」伪装成了待确认问题？
- 子 agent 交回来的「事实」是否都核过出处？指不到 `文件:符号` 的有没有降级为待确认？
