# 答案契约

非平凡回答时加载。一句话能答完的问题（如「35 是哪个状态」）直接答，不套模板。

## 结构

需求判断和梳理后的方案，第一份回复走 `../../../references/doc-shape.md` 的结论层。排查答案先给结论，再给证据。

1. **`结论`** —— 直接回答 + 对用户的影响。不要铺垫。
2. **`已确认范围`** —— branch、commit、静态/运行时边界、相关文件是否有未提交改动。
3. **`真实链路`** —— 简洁的 Proto → Service → Biz → Data → 依赖 追踪，带文件与行号。
4. **`状态解释`** —— 落库值、迁移守卫、派生/聚合含义，以及相关读侧。限定名必须带族，见 [state-protocol.md](./state-protocol.md) 规则 3。
5. **`仍需现场确认`** —— 只列 checkout 里拿不到的证据，并给出**可直接执行**的脱敏 SQL / 日志关键词 / Trace 条件 / 有效配置位置，每项说明它能排除哪种假设。
6. **`建议动作`** —— 最小可逆的下一步，按信息价值排序。

## 硬规则：不复述 L2 内容

**答案里只引用你亲自读过的文件，不复述知识库或文档的内容。**

复述是「看起来完整却漏链路」的直接来源：它让答案显得有据，实际上是把一份可能过期的二手材料重新包装，读者无从判断哪句来自代码、哪句来自文档。规则：

- 凡是写进取值的句子，必须能指到 ① 代码或 ⑥ 运行时证据。
- 知识库（③）只用来**选搜索目标**和**说明业务口径**；用它时要写明「知识库口径，已按 `<文件>` 核对」或「知识库口径，未核对」。
- 降级区（⑤）的内容不得出现在结论里，只能出现在「该文档已失效」的说明中。

## 完成标准

- 已标明当前 checkout。
- 相关端到端链路与状态维度都覆盖到了。
- 代码事实、文档、假设、运行时证据 visibly 分开。
- 冲突或失效的源已披露。
- 提出的下一个检查动作能区分剩余假设。
- 若写了卡片，含 provenance 与失效条件。

最后一条自查：**如果这个答案是错的，读者能从我给出的证据里发现它错了吗？**不能，就说明标签打得太满。
