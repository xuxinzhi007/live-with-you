# 证据阶梯与置信标签

事件类问题、或信源之间出现冲突时加载。

## 阶梯（①–⑤ 排「当前行为是什么」，⑥ 是另一根轴）

| 层 | 证据 | 说明 |
|---|---|---|
| ① | 当前 checkout 的代码与生成物 | 唯一权威。`*.pb.go` 等生成物同样算 ①，因为它们由当前 proto 生成 |
| ② | 覆盖当前路径的聚焦测试 | 证明这条路径真被执行过，而不只是「看起来会这样」 |
| ③ | `$KNOW/**` 对应**单个域**文件 | 业务口径、状态语义、排查入口的首选知识源。比仓库 `docs/` 新且更准。取值仍须回 ① 核对 |
| ④ | 仓库成文的工程约束（`.cursor/rules/*.mdc` / `.qoder/rules/` / `AGENTS.md` / `CLAUDE.md`）、`CONTEXT.md` | 工程约定与术语。多数 agent 不会自动加载别的 IDE 的规则目录，需要时显式 Read |
| ⑤ | **降级区**：`docs/`、`docs/support/` | **只作搜索线索，不可当结论**。凡与 ①③ 冲突，一律以 ①③ 为准，并在答案里点名该文档已失效。清单与原因见 [knowledge-sources.md](./knowledge-sources.md) |
| ⑥ | 线上日志、数据库行、Trace、部署有效配置 | 用于确认**某一次真实事件** |

⑥ 不参与 ①–⑤ 的排序竞争：**关于「线上那次到底发生了什么」，运行时证据压过一切静态推断。**静态审查能证明「可能的行为」与「代码约束」，但证不了部署的 commit、生效配置、请求载荷、行内实际值、并发竞争的胜者、外部系统的响应。

反过来也成立：⑥ 的**单次观测**不能证明业务规则。「线上这一行是这个值」不是「这个字段只会是这个值」。要把一次观测升级成规则，必须回到 ① 找到写入口与守卫。

## 冲突处理

信源不一致时，**呈现分歧本身**，不要偷偷选一个：

1. 点名当前胜出的源（哪一层、哪个文件、哪一行）。
2. 点名已失效的源，并说清它错在哪。
3. 如果失效的是降级区文档，按 [capture.md](./capture.md) 的强制规则写卡片——这类卡是全系统价值最高的产出，因为它记录的是失效本身。

## 置信标签

工作笔记里分开标注，答案里如实体现（不要把 Hypothesis 写成结论的语气）：

| 标签 | 含义 |
|---|---|
| Code-confirmed | 当前 checkout 直接支撑 |
| Test-confirmed | 本 checkout 的聚焦测试跑过这条路径 |
| Runtime-confirmed | 有部署侧日志/数据/配置支撑这次具体发生 |
| Hypothesis | 合理但缺决定性证据 |

## 引用规范

- 用仓库相对路径 + 有用的行号：`internal/biz/status.go:438`。
- **行号会随 commit 漂移**：卡片与长期知识里锚定函数名/const 块名，不锚行号；当次答案里可以给行号。
- 脱敏：token、凭据、个人数据、客户数据一律不写。示例请求与日志必须打码。
- 不把仓库默认配置当作线上有效配置。
