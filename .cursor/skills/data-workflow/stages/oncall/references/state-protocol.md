# 状态问题协议

问题里出现状态数字、状态名、迁移、卡住、进度不符、UI 状态时加载本文件。**本文件只有流程，没有取值表**——取值一律现场从代码读。

## 一、先分清五类「状态」

回答「现在是什么状态」之前必须确认用户指的是哪一类：

1. **持久化状态**：数据库列，如 `tb_episode.status`。
2. **并行状态**：同一实体的另一维，如 `tb_episode.data_parsed_status` 与 `qc_result`。
3. **派生展示态**：由多个字段计算、不落库，如 `DeriveEpisodeDisplayStatus()` 的结果。
4. **聚合态**：由多行计数与目标推导，如 Job/Collection 的 QC 状态、进度百分比。
5. **传输态**：Proto 暴露的枚举或裸数字字段。**不保证覆盖全部持久化状态**（仓库里确有 Proto 枚举少于库内状态的情况）。

第 5 类是最常见的错答来源：把 Proto 枚举当成完整状态目录，就会漏掉库里真实存在的状态。

## 二、状态族隔离规则（本技能的核心纪律）

### 规则 1 先定族，再解释数字

裸整数没有意义，必须解析成 `族(列)`：`EpisodeStatus(tb_episode.status)` / `CollectionStatus(tb_collection.status)` / `JobStatus(tb_job.status)` / `QCResult(tb_episode.qc_result)` / `NodeResult(...)`。

**用户只给数字、没给表/字段/页面/日志行时必须反问**，不要枚举全部候选含义当答案。枚举候选正是「一个 10 变成四个错答」的产生方式。反问一句的成本远低于答错。

### 规则 2 一次只加载一个族

只 grep 该族在 `internal/biz/status.go` 里的 const 块（`grep -n "<族名>" -A 40 internal/biz/status.go`），**绝不把全部状态族一起拉进上下文**。隔离边界就是 const 块；上下文里同时存在两个族的取值表，就一定会串。

### 规则 3 永远带限定词

写 `EpisodeStatus=20 (UPLOADED)`，不写 `status=20`。一个答案里出现两族时，必须以限定名成对出现，并显式说明「数字相同是巧合」。

### 规则 4 终态/生命周期结论只来自谓词，绝不来自数值大小

用代码里的谓词函数（如 `IsForsaken()`、`IsNodeResultPendingLike()`、`ForsakenTargetStatus()`），不要自己写 `>= 90`、`> 40` 之类的区间判断。**禁止按数值大小推断业务先后或终态**：异常态、展示态、聚合态、重试回退都会让区间判断产生错误结论。若找不到谓词，就逐个列出该族 const 块里的全部值并说明各自语义，而不是猜一个分界线。

### 规则 5 一族一上下文

问题真跨族时（如 Job → Collection → Episode 的进度对不上），**每族各自成小节、各自给信源**，不要做合并对照表。合并表本身就是交叉污染：它邀请读者横向比较本不可比的数字。

## 三、碰撞确实存在（这是怀疑的动机，不是查找表）

同一个数字在不同族里含义完全不同，且没有任何规律：

- `10` = Job 的已发布态 / Collection 的采集中 / Episode 的已采集 / QCResult 的正常
- `20` = Job 的暂停 / Collection 的冻结 / Episode 的已上传 / QCResult 的设备异常
- `90` = Job 的已删除 / Collection 的异常 / Episode 的失败

（以上取值随 commit 变化，**只用于说明「碰撞存在」这一事实**；回答时必须现场重新读取该族的 const 块。）

## 四、把状态当多维调查，不当单一字段

不要假设叫 `status` 的字段就是整个状态机。每个状态问题都要识别：

- **持久化**：表/列，以及权威的 Go const 位置。
- **传输**：暴露给调用方的 Proto 枚举或裸数字字段。
- **迁移**：每一个写入口、旧状态守卫、事务边界、重试/重置路径、终态例外。
- **派生**：由多列/多行算出的展示态或聚合态。
- **消费**：SQL 过滤、资格判定、进度计数、导出、队列、响应映射。
- **归属**：data-service 自己写，还是 scheduler 写，还是外部系统上报。

解释一个状态/计数/可见性结果/展示字段时，**读侧和写侧都要追**。「值已经写进去了」不代表用户看得见——列表还受 tenant/group/RBAC、软删、关联表、读模型、分页和派生筛选影响。

## 五、固定核验清单

1. 当前 branch/commit 是什么？相关文件有没有未提交改动？
2. 用户说的状态来自哪张表、哪个 API 字段、哪个页面、哪条日志？
3. 它是持久化、并行、派生、聚合，还是外部状态？
4. 当前值、预期值、最近更新时间、错误字段、关联 ID 分别是什么？
5. 哪些写入口能产生目标值？各自允许哪些旧值？
6. 写入是否在事务、CAS、队列或 scheduler 内？失败与重试如何表现？
7. 哪些读侧条件会隐藏或重新解释这个值？
8. 要确认这次线上事件，还缺哪一条日志、数据行、Trace 或有效配置？

第 8 项答不出来，说明还停在静态推断，不能说「已确认」。
