# Quality Gate（质量门禁）

编码完成不等于可以提交。本技能用命令的真实输出证明改动质量。改动审核先判断会不会出事，本技能在审核通过之后跑。规范对照在 `../change-review/references/standards-spec.md`。

**分工**：本技能只管编译、单测、覆盖率、生成物一致性。接口契约（进程内契约测试、proto 破坏性 diff、场景回放）归 `../interface-test/SKILL.md`，四态裁决也只在那边出。本技能 G4 发现 Breaking 时**移交**给它，不自己下 PASS/FAIL。

## 何时执行

- 改动审核结论为可继续之后
- 审核指出的问题改完，并再次审核通过之后
- 提交前，作为最终闸门，必须全绿

## 检查项（按序执行）

### G0 圈定改动范围（先做，一切检查锚定它）

- 先跑 `git status --short` 拿未提交改动清单；无未提交改动时问用户要 commit 范围（如 HEAD、HEAD~1..HEAD）。
- 产出改动文件清单，后续 G1-G6 只针对这份清单，禁止扩大到全项目。
- 清单分类：Go 文件 / proto / 配置 / SQL / 文档。注意：`go:embed` 引用的文件（如 configs/tag/system_tags.json）算 **Go 逻辑相关改动**，G2/G3 不得跳过。

### G1 编译与格式

- `go build ./...` 必须通过（例外说明：编译有缓存，全量成本极低且能捕捉跨包编译错误，这条是唯一允许全量的命令）。
- wire 有改动：按 Makefile 重新生成依赖注入代码。
- `gofmt -l`、`goimports -l` 只对 G0 清单里的 Go 文件执行，输出必须为空。

### G2 单元测试（只跑受影响包）

- 只跑：G0 清单涉及的包 + G4 判定的直接受影响包，逐包 `./scripts/test-unit.sh -p <pkg>`。
- 禁止不带 `-p` 的全量模式；禁止「顺手跑一下其他包」。
- 只改 proto/配置/SQL 且无 Go 逻辑变化的，跳过并在报告标注理由（go:embed 的配置除外，见 G0）。
- 配置类文件（JSON/YAML）改动：只验证 diff 里的改动条目（该条目在整体结构中的位置、取值合法性），不重验全文件、不做全树 dump。

### G3 覆盖率

- 新增导出函数/方法：`make test-coverage-func PKG=<pkg> FUNC=<name>` 覆盖率大于 0，或存在用例名直接对应。
- 改动的业务分支（biz/data 新增 if/switch 分支）：必须有断言触达；覆盖不到的写明原因（如外部依赖），不允许默认跳过。
- 门线是「新代码有测试触达、改动文件既有测试保持通过」，不设全项目绝对覆盖率指标。

### G4 影响验证（会不会影响别处）

1. 列出 G0 清单里改动的符号：函数、方法、结构体、proto 字段、配置项。
2. 检索每个符号的调用方。**收敛规则：只对直接调用方所在包跑回归**（`./scripts/test-unit.sh -p <pkg>`）；二级传导（调用方的调用方）只列出、标注风险，不跑测试。调用方横跨 3 个以上包时，先用读代码判断哪些包行为真受影响，只跑行为受影响的包。
3. 回归失败 = 影响真实发生，必须修复或回滚。不允许「这个失败与本次无关」式带过——除非能证明失败在改动前就存在（git stash 后复跑通过、恢复后再失败）。
4. 签名、返回值、行为语义、proto 字段号发生变化 → 标记 Breaking Change，移交 `../interface-test/SKILL.md` 跑契约门出裁决，同时停下来向用户报告影响清单，拍板前不进入提交。

### G5 生成文件一致性

- proto 有改动：必须重新生成，命令与生成物清单以 `Makefile` 目标为唯一正确副本（`make api` / `make api-one PROTO=<路径>`；工程事实走知识层 `$KNOW`，不抄文档二手结论）。git diff 中 `*.pb.go` 的改动只能来自生成。
- 发现手改 pb 的一律打回重做。

### G6 复用门禁

- 含 Go 改动必须调用 `reuse-gate` 技能执行 R14-R18（先搜再写、禁平行实现、死代码）。

## 输出格式

```
质量门禁报告
G0 改动范围   改动文件数与分类（Go x / proto x / 配置 x / ...）
G1 编译与格式   ✓ / ✗（原因）
G2 单元测试     ✓ 通过包列表 / ✗ 失败包与用例 / 跳过（理由）
G3 覆盖率       ✓ 新增函数触达情况 / ✗ 未触达清单
G4 影响验证     ✓ 回归通过包列表 / ✗ 受影响调用方 / ⚠ Breaking 清单
G5 生成文件     ✓ / 跳过（无 proto 改动）
G6 复用门禁     ✓ / ✗ 结论
结论：全部通过，允许提交 / 未通过，先修复 Gx
```

报告落盘 `specs/<feature>/quality.md`（工件树见 `../../references/artifact-tree.md`）。**每条 ✓ 后面必须跟命令与其真实输出摘要**；没有输出的 ✓ 视为未跑，文档审计门会打回。

## 命令纪律（减少人工确认）

- 检索、读文件、找调用方：优先用内建工具（Read/Grep/Glob），不用 Bash 的 cat/grep/管道——内建工具不触发权限确认。
- 验证命令：只用项目现成命令（`go build`、`test-unit.sh -p`、`make test-coverage-func`、proto 生成命令以 `Makefile` 目标为准、`gofmt -l`）；不现场发明验证脚本。工程约束文件的落点按 `../../references/project-index.md` 解析（`.cursor/rules/` → `.qoder/rules/` → `AGENTS.md` → `CLAUDE.md`），不要把某一个 IDE 的目录名当成事实。
- 禁止重定向、`tee`、管道拼接命令（`>`、`>>`、`|`）——这是触发权限确认的直接元凶；需要看输出就直接读终端输出。
- 必须用自造命令时（项目命令覆盖不了），先用一句话向用户说明要跑什么、为什么，再执行。

## 原则

- 一切以命令真实输出为准，禁止「应该没问题」式断言；没跑过的检查项不许标 ✓。
- 检查范围锚定 G0 清单：验证密度随改动范围缩放，小改动小跑，不因「顺便」扩大验证面。
- 失败项修复后重跑失败项；若修复涉及 Go 代码变动，从 G1 整链重跑。
- Breaking Change 永远停下来问人，不静默带过。
