# Impact Assessment（影响面与爆炸半径）

回答一个问题：**这次改动会打到谁，打到了怎么收场。** 落 `impact.md` 前读 `../../references/doc-shape.md`：主活是速查，第一屏是四轴各一行。

产出是可核对的清单，不是形容词。每一项要么带证据（`文件:符号`、grep 命中数、命令输出），要么显式写 `UNVERIFIED <原因>`。**没有第三态**——空白项和「应该没问题」都算未做评估。

判定细则与 grep 配方见 [`references/blast-radius.md`](references/blast-radius.md)，动手前读一次。

## 输入

- 已明确的改动意图（要改哪个 proto / biz / data / 状态 / 配置）。
- `$REPO` 的当前 checkout。评估基于**代码现状**，不基于技术方案里的设想。
- 若来自 `requirement-analysis`，拿它的「事实清单」当起点，但每条仍要自己验一次。

## 四轴清单

### 轴 1 调用方（谁会因此改变行为）

| 查什么 | 证据形式 |
|---|---|
| 改了 proto 字段/RPC：谁是调用方 | `api/**/*.proto` 命中行 + 生成的 `*.pb.go` 引用点计数 |
| 改了 biz 方法签名或语义：谁调它 | grep 方法名的调用点清单（含测试） |
| 改了返回结构/默认值：谁读它 | service 层转换点 + 前端可见字段名 |
| 改了 SQL 谓词/排序/分页：哪些列表和计数共用它 | 共用同一 Repo 方法的全部调用方 |

**契约影响单独标**：删字段、删 method、可选变必填、语义变更（同字段换含义）= breaking，必须写「谁需要跟着改」。

### 轴 2 状态机（新增/修改枚举的全库追踪）

新增一个状态值或枚举常量时，**必须全库追踪它的每一个消费点**，不能只看写入方：

- `switch` / `if` 链里是否列举了状态（漏一个 = 静默走 default）
- 白名单、allowlist、`map[Status]bool`、`In(...)` 集合
- SQL 过滤条件、列表默认可见范围、进度计数、导出、队列投递
- 前端展示映射、终态判定函数（如 `IsXxx()` 系列）

输出格式：`消费点 → 是否需要改 → 证据`。任何「不确定是否要改」写成 `UNVERIFIED`，不许留空。

### 轴 3 租户与权限（谁能看见、谁能改）

| 查什么 | 证据形式 |
|---|---|
| 新增入口的权限码 | proto option 里的 `code`/`description` 原文 |
| 数据范围口径 | 复用了哪个 `apply*Scope` / `FindByJobID` vs `FindByJobIDAndTenantId` |
| 管理员例外 | 是否存在 SYS_ADMIN 之类跨租户分支，改动是否绕过它 |
| 租户缺失时的行为 | 整批拒绝还是部分成功，错误码是什么 |

**跨租户读写路径必须点名**，写「本次改动是否引入新的跨租户可达路径：是/否 + 证据」。

### 轴 4 回滚（出事怎么收场）

- 代码回滚步骤（编号）；是否依赖发布顺序（先后端/先前端/先配置）。
- 数据回滚步骤：新增列/新增行/已写入的状态能否逆向；**不可逆 + 无备份 = 阻塞**。
- 能否只回滚一半：开关在哪、默认值是什么、关掉后旧数据怎么处理。
- 灰度不可行时说明为什么（只读 / 幂等写 / 可重放 三种允许情形之一）。

## 维护性三查

| 查什么 | 判定 |
|---|---|
| 是否新增第 N 份副本 | 同语义逻辑在仓库里出现第几次（grep 关键表达式，不凭印象）。第 2 次必须复用已有实现，第 3 次才允许抽象 |
| 模块深浅 | 新增导出符号的数量，每个能否说清唯一调用方；只新增「参数转换层」= 浅模块，判负债 |
| 腐化点 | 6 个月后加一个维度要改几个文件、几处判空。>3 必须给收口点，或写进「已知代价」并说明接受理由 |
| 这次新增的债 | 临时判断、复用字段号、绕过已有抽象。只记这次 diff 新欠的。存量债写一条线索，不在这次改动里偿还；要还就另开 `change` 或 `bugfix` |

## 禁止

- 用「影响较小」「风险可控」「基本没问题」代替证据。
- 把技术方案里的设想当现状（方案可能已过期，以 checkout 为准）。
- 只评写入方不评读取方——状态类改动最常见的漏项就是读取方。
- 评估范围外溢：只评本次 diff 涉及的链路，不做全仓审计。

## 产物

落 `specs/<feature>/impact.md`（模板 `$PLUGIN_ROOT/templates/impact-template.md`）。工件树与命名见 `../../references/artifact-tree.md`。

一屏摘要格式：

```
影响面评估 <feature>
调用方    proto ×N / biz 调用点 ×N / 共用 Repo 的列表与计数 ×N   breaking: 有|无
状态机    新增 <枚举值>；消费点 N 处，需改 M 处，UNVERIFIED K 处
租户权限  权限码 <code>；范围口径 <apply*Scope>；跨租户新路径: 无
回滚      代码 N 步 / 数据 N 步 / 可半回滚: 是|否（开关 <名字>，默认 <值>）
维护性    副本 第N次 / 新增导出符号 N 个 / 6 个月加维度改 N 文件
阻塞项    无 | 第 x 轴：<一句话>
UNVERIFIED ×N（逐条列出，含需要什么证据才能确认）
```

## 自查（输出前）

- 四轴 + 三查每一项都有证据或 `UNVERIFIED`，没有空白？
- 新增枚举是否真的做了全库消费点追踪（含 SQL、白名单、前端映射）？
- breaking 契约变更是否点名了「谁需要跟着改」？
- 回滚步骤是否可执行（别人照着做能回到改前状态）？
- 是否只评了本次范围，没有顺手做全仓审计？
